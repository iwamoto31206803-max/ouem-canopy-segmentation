# R1a — Offline dataset contract v1

This is a new input path for R1/R2. G0–G3-A code, manifests, GeoTIFFs,
checkpoints and historical acceptance remain unchanged. No Trainer, acquisition,
GPU operation or R1b visual/legal adjudication is implemented here.

## Identity and schema

`scripts/r1_dataset.py` uses `schema="ouem-r1-dataset-v1"` and
`source_generation="zenodo-11617167-v1.0.0"`. The number of samples is any
positive integer; sizes may differ. A one-split dataset is allowed, but cannot
establish independence from future, unlisted samples.

`dataset_id` is `ouem-r1-` followed by the **full** SHA-256 of canonical manifest
bytes. Canonicalization deep-copies the JSON object, removes only the top-level
`dataset_id`, sorts `samples` by unique integer `image_id`, and serializes with
Python `json.dumps(sort_keys=True, separators=(',', ':'), ensure_ascii=False,
allow_nan=False)`, then UTF-8 encoding, **without BOM or terminal newline**.
Other arrays retain their order; strings undergo no Unicode normalization.
JSON object keys must be unique; NaN/Infinity are forbidden. Numeric spellings
follow Python JSON serialization (1 and 1.0 differ); producers should use the
provided `identify()` function. Every other field, including additional evidence
and acceptance declarations, contributes to identity. Changing evidence requires
a new ID. File-byte manifest SHA-256 is a separate, externally pinned identifier.
Neither ID nor file SHA is a signature or a substitute for trusting evidence.

Top level: `schema`, `source_generation`, `dataset_id`, `samples`.
Each sample contains:

| Field | Contract |
| --- | --- |
| `image_id`, `oam_id` | Unique integer image ID >=0; nonempty source-group ID |
| `split`, `official_split`, `validation_fold` | `train`/`val`; official `train` only; integer folds 1–4/0 respectively |
| `source_generation`, `threshold` | Exact generation above; threshold 0.5 |
| `grid` | `crs`, six-number affine `transform` in a,b,c,d,e,f order, `bounds` [left,bottom,right,top], positive integer `shape` [height,width] |
| `products` | Exactly `rgb.tif`, `canopy_fraction.tif`, `canopy_mask.tif`, `valid_fraction.tif`; each has `path` and lowercase 64-hex `sha256` |
| `source` | `dataset="restor/tcd Zenodo"`, `revision="zenodo-11617167-v1.0.0"`, `image_sha256`, `annotation_sha256`, `original_source_id`, `footprint_wgs84` |
| `rights` | `image_license`, `annotation_license`, `original_source_license` (each explicitly `CC-BY-4.0`), `attribution`, `evidence_ref`, `evidence_sha256` |
| `labels` | `policy="upstream_nonzero_binary_with_review"`, `categories=[1,2]`; retain `per_segment_category_status` if unknown |
| review objects | `category_review`, `validity_review`, `independence_review`, `external_independence_review`, `r1_review`; described below |

Paths are exactly `<split>/<image_id>/<product-name>`, relative to a relocatable
dataset root. Absolute paths, traversal, alternate separators, duplicate paths,
symlinks and Windows reparse points/junctions (including ancestors) are rejected.
The root must be an ordinary local directory; copy data out of linked folders.
The verifier does not modify data or require network access. Unreferenced files
are not dataset members and are not opened or certified.

Each review object has `status="PASS"`, a nonempty `evidence_ref`, an
`evidence_sha256`, and `source_hashes` with exactly `image_sha256` and
`annotation_sha256`, equal to the sample's source hashes. These are **R1b
source-bound review assertions**, not booleans auto-generated by this verifier.
`category_review` must explain the upstream nonzero RGB union, approved COCO
categories and limitations. It does not prove a per-panoptic-segment category
mapping: COCO annotation IDs must never be treated as segment IDs. Missing
crosswalks remain explicitly NOT_VERIFIED even if an R1b reviewer accepts the
official binary semantic policy. Record uncertainty in the evidence; do not
fabricate PASS or upgrade an existing HOLD merely to satisfy the schema.

`independence_review` concerns the manifest cohort. The separate
`external_independence_review` must cover official holdout and unlisted neighboring
or aliased sources: it additionally requires
`scope="official_holdout_and_unlisted_neighbor_sources"` and the SHA-256 of the
reviewed metadata catalog in `catalog_sha256`. Like the other reviews it requires
source-hash binding and a hashed evidence reference. Missing/wrong scope, catalog
hash or binding is acceptance HOLD. R1b must document the catalog revision and
coverage, identity aliases, footprint/proximity methods, and unresolved gaps in
that receipt, without reading holdout pixels. A receipt is an external assertion;
this offline validator does not perform or certify that catalog investigation.

Evidence references may be sanitized receipt/ledger references or public URLs;
private STAC/contact details and source images stay outside Git. This offline
validator checks **record completeness and source binding**, not the contents
of remote/external evidence documents or source-image bytes. Those require R1b
inspection and hashing. The manifest's recorded SHA is not evidence that the
source archive was freshly read. Final commercial rights approval is separate.

## Technical checks and R1 acceptance

Each image and the aggregate report have separate `technical` and `acceptance`
statuses, with reason lists. No historical `training_eligible` or
`accepted_for_M1_7_smoke` grants R1 acceptance.

* Technical FAIL: malformed contract/identity/split, missing file, bad hash,
  unsafe path, dtype/channel/shape/grid/CRS/bounds mismatch, invalid values or
  mask/fraction disagreement. CRS equality uses rasterio CRS semantics;
  affine and shape must match exactly, bounds use absolute tolerance 1e-8
  in CRS units and zero relative tolerance. Affines must be finite/invertible.
* Technical HOLD: nodata declaration, any non-valid per-band raster mask, or
  any `valid_fraction != 1`. No implicit nodata, black-pixel rule or partial-area
  learning policy is introduced. Black RGB can be legitimate; source-bound
  validity review is still required to exclude artificial wedges/uncertainty.
* Technical PASS: all referenced products passed their checks. RGB is 3-band
  uint8; binary mask is 1-band uint8 0/1; fractions are 1-band float32, finite
  in [0,1]. The mask must equal `(canopy_fraction >= 0.5)`. Uniform 0/1 is kept.
* R1 acceptance HOLD: missing/conflicting rights, missing source identity or
  footprint, missing category/validity/independence/R1 review, same-split duplicate
  source, or a conservative cross-split proximity warning. Technical success
  cannot resolve these. Invalid known cross-split source/footprint leakage is
  acceptance FAIL. Product failure also prevents acceptance.
* R1 acceptance PASS: technical PASS and all explicit review assertions and
  independence guards pass. This is a machine check of supplied R1b evidence,
  **not an independent visual/legal certification**.

Source-group, original-source identity and exact source-image byte-hash comparisons
are dataset-wide. A repeated
source within one split is conservatively HOLD pending R1b, consistent with the
initial distinct-source plan. Opposite-split identical sources or geographic
overlap fail acceptance. Compare the union of product and declared original-source
WGS84 bounding envelopes, and retain the pilot's conservative 1km proximity HOLD
using WGS84 geodesic center distance minus corner radii. Bounding boxes may
over-reject irregular scenes; no automatic geometric repair is attempted.
Dateline/invalid envelopes cannot prove independence. Missing source footprints
remain HOLD even if product tiles do not overlap. Independence from sources
outside this manifest is NOT_VERIFIED; R1b must review the actual original-source
identity/extent, broader holdout separation, and near-duplicate scenes. Official
test/holdout records are rejected without opening their pixels.

`original_source_id` must be an R1b-verified canonical scene/object identity,
not an expiring URL or merely another copy of `oam_id`. Its declared envelope
must contain the product envelope (1e-8 degree containment tolerance); a conflict
is HOLD. Equivalent source IDs under aliases cannot be discovered from these
strings alone and remain an R1b evidence obligation.

## CLI and R2 integration

No new dependencies: numpy, rasterio and pyproj are already used in preprocessing.
Hash streaming, product names and generation are reused from the frozen G0 module;
its fixed-ten acceptance verifier is **not** rewritten or applied as R1 acceptance.
R1 implements the same raster checks separately because partial validity must be
reported as HOLD rather than G0's unconditional rejection.

Prepare a new manifest from R1b receipts and recorded product hashes. In Python,
`manifest['dataset_id'] = r1_dataset.identify(manifest)` seals its content; write
it once to a new path, then pin its file SHA. `read_manifest()` rejects duplicate
JSON keys and nonfinite constants. Do not edit a sealed manifest in place.

```powershell
$manifestHash = (Get-FileHash $manifest -Algorithm SHA256).Hash.ToLowerInvariant()
.\.venv\Scripts\python.exe scripts/r1_dataset.py `
  --root $datasetRoot --manifest $manifest --manifest-sha256 $manifestHash `
  --report $newReportPath
```

Exit codes: 0 = technical/R1 PASS, 2 = HOLD, 1 = FAIL. Reports require a fresh
file; an existing report is never overwritten. Inspect both statuses, reasons
and `product_counts`; no exception should be interpreted as success.

`verify(root, manifest)` produces the complete dataset audit report, including
HOLD/FAIL results. `preflight(root, manifest)` runs that audit and returns an
in-process, immutable loading context **only when the entire dataset's technical
and acceptance statuses are PASS**. Failure in an unselected image also blocks
context creation. Use `load_sample(context, image_id, expected_split)`; passing a
manifest, report or no context is rejected. The context binds a deep-copied
manifest snapshot to its resolved dataset root, so callers cannot substitute a
different root/manifest or change the checked snapshot by mutating their original
dictionary. Only the selected four products are rehashed/rechecked during loading.

```python
context = r1_dataset.preflight(dataset_root, manifest)
arrays = r1_dataset.load_sample(context, image_id, "train")
```

The context is an accidental-misuse guard, not a security boundary against code
deliberately accessing private internals; it must not be persisted as a substitute
for fresh preflight after restart. R2 must pin dataset ID and file-manifest SHA,
stage immutable bytes, and rerun preflight after resume/relocation. Unselected
files changed after preflight are detected when selected, not continuously; no
filesystem locking or whole-dataset rehash on every step is promised. No Trainer
is introduced.

`product_counts` records `expected`, `attempted`, `pass`, `hold`, `fail` and
`not_attempted`. Products are checked in sorted filename order; each attempted
product records its own status/reasons. PASS means that file's hash, grid,
channels/dtype, value range and declared coverage checks passed. HOLD means its
coverage is partial/ambiguous. A file failure preserves earlier product results
and leaves remaining products of that image not attempted; other images continue.
Cross-product fraction/mask threshold checking is a **sample-level** check: four
files may individually PASS while the sample FAILs this check. Thus no product
counter implies sample acceptance. `samples_fully_technical_pass` counts only
sample technical PASS; the ambiguous old `products_verified` field was removed.

The report separately records `independence.within_manifest` (the automated
declared-source/footprint check) and `independence.external_sources` (always
`NOT_VERIFIED` by this offline program, plus `review_assertions_complete`). Even
complete external assertions do not become a claim that the validator inspected
official holdout or neighboring sources. Acceptance PASS checks the supplied
R1b assertions; missing assertions are HOLD. R1b owns the actual external audit.

## Read-only Zenodo10 compatibility result

```powershell
.\.venv\Scripts\python.exe scripts/r1_dataset.py `
  --root $existingZenodo10Root `
  --manifest docs/implementation/M1_7_G0_MANIFEST.json `
  --manifest-sha256 c2f4ccd56da8770cd73ef1db299d67d5528dcab8ea0051da1c2d5f8174a850ca `
  --legacy-g0 --report $newReportPath
```

`--legacy-g0` makes an in-memory projection only. The frozen G0 schema/identity
is checked first; byte-level manifest pinning is mandatory. Historical rights
and visual receipts are retained under `legacy_*`, not rewritten into R1 PASS.
No projected data or original manifest is modified.

Measured locally on Windows/Python 3.11.9: **10 images / 40 products technical
PASS; all 10 R1 HOLD**. See [machine-readable report](R1A_LEGACY_COMPATIBILITY.json).
The input pinned manifest is unchanged. Reasons include missing exact original
source identity/footprint and R1-specific rights/category/validity/independence
review assertions. Existing per-segment category validation remains NOT_VERIFIED.
This result neither revokes historical smoke acceptance nor promotes it.
